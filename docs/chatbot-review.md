# 챗봇 검토 기록

검토일: 2026-08-20  
범위: 일반 챗봇, 보안 챗봇, 대화 저장소, RAG/임베딩, 예측 모델 연동, 프런트 UI

## 결론

현재 챗봇은 예측 모델과 SSE 스트리밍 자체는 동작하지만, 인증·대화 소유권 검증·민감 데이터 보관 방식에 높은 위험이 있다. 이번 수정으로 일반 챗봇의 메뉴별 답변 형식, 화면 컨텍스트 DB 폴백, Qdrant 장애 시 중복 임베딩 모델 초기화는 보완했다. 보안 챗봇은 MariaDB, Qdrant, 로컬 vLLM이 모두 준비돼야 실제 답변을 제공할 수 있다.

## 재시험 결과

아래 표는 메뉴별 답변 수정 전의 기준 성능이다.

테스트에는 프로젝트가 지정한 임베딩 모델 `BAAI/bge-m3`를 로컬 경로에서 사용했다. 가중치 파일(2,271,145,830 bytes)은 공급처 SHA-256과 일치함을 확인했다. 이 모델은 답변을 생성하는 LLM이 아니라 RAG 및 대화 기억 검색용 임베딩 모델이다.

| 경로 | 결과 |
| --- | ---: |
| 일반 챗봇 첫 자유 질의 | 34.8초 |
| 일반 챗봇 반복 자유 질의 중앙값 | 2.06초 |
| 예측 포함 챗봇 반복 질의 중앙값 | 2.55초 |
| 예측 모델 계산 중앙값 | 486ms |
| 백엔드 프록시 포함 예측 질의 | 2.61초 |
| 일반 챗봇 스트리밍 | 2.72초, `meta`/`delta`/`done` 이벤트 확인 |
| 보안 챗봇 | 141ms, `enqueue_failed` 오프라인 응답 |

일반 챗봇의 내부 `timing.total_ms`는 0.2~12ms로 응답됐으나, 실제 왕복 시간은 약 2초 이상이었다. 히스토리 벡터 검색과 Qdrant 연결 재시도 시간이 해당 지표에서 빠져 있기 때문이다.

### 시험 환경의 한계

- MariaDB와 Qdrant가 실행되지 않은 상태에서 일반 챗봇의 로컬 임베딩·템플릿·예측 경로를 검증했다.
- 보안 챗봇의 실제 RAG/vLLM 생성 답변은 MariaDB 큐, Qdrant 문서 인덱스, 로컬 vLLM이 모두 없어 검증하지 못했다.
- 활성 외부 LLM과 키 저장소의 실제 설정은 노출하지 않았으므로 생성형 답변의 품질·비용 평가는 별도 환경에서 필요하다.
- 테스트 모델은 임시 경로에만 받았으며, 저장소 설정이나 소스 파일은 변경하지 않았다.

## 메뉴·카테고리 컨텍스트 재시험

아래 표는 메뉴별 답변 수정 전에 확인한 문제를 기록한 것이다.

사용자 질문 `현재 화면을 요약해 주세요.`에 메뉴별 페이지 컨텍스트와 서로 다른 식별값을 넣어 일반 챗봇을 시험했다. 대시보드, 이슈, 지식 메뉴 모두 해당 메뉴의 데이터가 답변에 반영되는 것은 확인했다.

| 메뉴/경로 | 결과 | 판정 |
| --- | --- | --- |
| `/dashboard` | AI 서비스 직접 호출 시 2.14초, 위험 LOT 데이터가 답변에 포함 | 메뉴 데이터는 인식하지만 `primary_table`, `items` 등을 포함한 JSON 나열형 템플릿이었다. |
| `/issues` | 백엔드 경유 12.12초, 이슈 식별값이 답변에 포함 | 이슈 데이터는 구분했으나 이슈 우선순위·담당·다음 조치를 해석하지 않고 JSON 형태로 표시했다. |
| `/knowledge` | 백엔드 경유 2.09초, 지식 식별값이 답변에 포함 | 지식/인수인계 데이터를 구분했으나 검색 요약이나 후속 행동 대신 데이터 나열형 응답이었다. |
| 선택 LOT 상태 질문 | AI 서비스 직접 호출 시 2.15초 | 선택된 LOT ID를 반영한 짧은 고정 요약은 동작했다. 다만 이 예외 경로도 추천 조치·우선순위까지 만들지는 못한다. |

### 이번 처리 결과

일반 챗봇이 화면 데이터를 그대로 나열하지 않고 메뉴의 업무 목적에 맞게 요약하도록 수정했다. 외부 LLM을 쓰는 경로에도 같은 메뉴별 출력 계약을 전달하며, 외부 LLM이 없을 때는 로컬 템플릿이 동일한 구조로 답한다.

| 검증 항목 | 처리 후 결과 |
| --- | --- |
| `/dashboard` 일반 응답 | 1,446ms, 위험 LOT 건수·우선 확인 LOT·근거 지표·다음 확인 순서 출력 |
| `/issue` 일반 응답 | 28ms, 열린 이슈·고위험·담당자 미지정·조치 대기·처리 순서 출력 |
| `/knowledge` 일반 응답 | 27ms, 과거 이슈·인수인계·선택 문서·후속 확인 출력 |
| `/dashboard` SSE 스트리밍 | 1,340ms, `meta`/`delta`/`done` 이벤트와 메뉴별 답변 확인 |
| `/issue` 선택 항목 응답 | 1,237ms, 관련 LOT·위험도·담당자·처리 상태·내용을 사용자 문구로 출력 |
| 내부값·원시 데이터 노출 검사 | 내부 경로(`/issue` 등), `HIGH`/`pending`, `page_payload`, `primary_table`, `items` 및 JSON 객체 나열 없음 |
| Qdrant 장애 동시 초기화 검사 | 동시 3회 호출이 한 번의 연결 확인만 수행했고, BGE 임베딩 모델은 로드되지 않음 |

처리 내용은 다음과 같다.

1. 메인, 대시보드, 이슈, 지식, 문의, SPC, 설정 메뉴별로 답변 항목과 우선순위를 정의했다.
2. 답변에서 내부 라우트와 `포커스` 같은 구현 용어를 제거하고, 위험도·처리 상태 코드값을 한국어 업무 문구로 변환했다.
3. `현재 화면을 요약해 주세요.`처럼 목적격 조사 `을`을 쓰는 문장도 화면 요약 의도로 인식하도록 보완했다.
4. 페이지 컨텍스트 DB 재조회는 기본 1.2초 안에 끝나지 않으면 프런트가 이미 전달한 현재 화면 데이터로 폴백한다.
5. 단기 대화 이력이 없으면 장기 벡터 이력 검색을 생략한다.
6. Qdrant 연결을 먼저 확인한 뒤에만 BGE 모델을 로드하며, 초기화 잠금과 30초 재시도 유예를 적용했다.

시험 환경에는 MariaDB가 없어 백엔드의 레거시 세션 저장소를 `memory`로 두고 검증했다. 따라서 실제 운영 DB 연결 상태, 외부 생성형 LLM이 활성화된 답변 품질, 보안 챗봇 RAG 답변은 별도 통합 시험이 필요하다.

### 초기 메뉴별 테스트에서 확인했던 문제

1. **메뉴별 답변 스키마가 없다.** 현재 경로는 컨텍스트를 자르고 전달하지만, 외부 LLM이 비활성인 기본 경로는 `현재 화면 (/경로)`와 페이지 JSON을 그대로 붙인다. 메뉴에 따라 “대시보드 위험 요약”, “이슈 조치 현황”, “지식 문서/인수인계 요약”처럼 다른 답변 구조를 만들지 못한다.
2. **대시보드/이슈 컨텍스트 수집이 동기 DB 재조회에 묶여 있다.** DB가 없던 시험에서 대시보드는 `enrich_ms=20,027ms`, 전체 39.4초가 걸려 클라이언트 30초 제한에서 시간 초과했다. 이슈 메뉴도 컨텍스트 수집에 10.0초가 걸렸다. 페이지 데이터 보강 실패는 즉시 기존 화면 데이터로 폴백해야 한다.
3. **카테고리별 질문 의도가 제한적이다.** `이 화면 요약`, 선택 LOT 식별, SPC 부재 같은 일부 규칙만 별도 처리한다. 메뉴별로 무엇을 묻는지(위험 우선순위, 미조치 이슈, 인수인계, 문서 근거)를 분류하고 해당 형식으로 답하는 라우팅이 필요하다.
4. **실제 생성형 LLM 기준 검증이 남아 있다.** 현재 외부 LLM 키/활성 모델이 없는 시험 환경에서는 템플릿 경로만 검증됐다. LLM이 켜진 경우에도 메뉴별 출력 계약을 지키는지 별도 평가셋으로 확인해야 한다.

| P2 | UI 구조 | 일반/보안 챗봇이 스레드·로컬 저장·스트리밍 처리 로직을 중복 구현한다. | 보안 수정과 기능 개선이 두 컴포넌트에서 서로 다르게 적용될 가능성이 높다. |
| P2 | UX | 요청 취소를 위한 내부 `AbortController`는 있으나 명확한 사용자 취소 UX가 부족하고, 입력창은 긴 다중 줄 질의에 불리하다. | 장시간 응답·오프라인 상태에서 사용자가 대기 또는 복구 상태를 제어하기 어렵다. |

## 권장 조치 순서

1. 모든 채팅 및 LLM 키 API에 인증을 적용하고, 서버 세션의 사용자 ID만 사용한다.
2. 일반·보안 스레드 모두에서 메시지 로드/삽입 전에 소유권을 확인한다.
3. 보안 대화와 출처 원문을 `localStorage`에서 제거하고, 실제 서버 삭제 및 보존 정책을 구현한다.
4. 남은 대화 히스토리/Qdrant 처리 시간을 응답 성능 지표에 포함한다. 연결 선확인, 짧은 timeout, 실패 cooldown은 이번 수정에서 적용했다.
5. 보안 챗봇의 의존성 준비 상태를 사전 점검해 사용자가 실제 RAG 가능 여부를 알 수 있게 한다.
6. 예측 근거(`top_risk_factors`)를 채우고 판정 규칙과 표시 확률을 함께 설명한다.
7. 백엔드 build 오류와 프런트 lint 오류를 해결한 뒤, 실제 활성 LLM 기준의 품질·비용·지연 평가를 수행한다.
